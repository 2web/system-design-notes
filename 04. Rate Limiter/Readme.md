# Глава 4. Проектирование ограничителя запросов (Rate Limiter)

## Введение
В этой главе рассматриваются проектирование и реализация ограничителя запросов (rate limiter) — компонента системы, который контролирует частоту запросов, отправляемых клиентами или сервисами. Ограничители запросов крайне важны для предотвращения злоупотреблений, снижения затрат и обеспечения стабильной работы серверных ресурсов. Примеры применения: ограничение количества публикаций, создания аккаунтов и получения бонусов.

## Преимущества ограничения частоты запросов
- **Защита от DoS-атак (DoS — Denial of Service, «отказ в обслуживании»):** блокировка избыточных вызовов, чтобы не допустить исчерпания ресурсов.
- **Снижение затрат:** ограничение лишних запросов снижает расходы на серверы.
- **Предотвращение перегрузок:** отсеивание избыточных запросов стабилизирует работу серверов.

## Шаг 1. Понимание задачи
### Ключевые функции
- Ограничитель запросов к API (Application Programming Interface — программный интерфейс приложения) на стороне сервера.
- Поддержка нескольких правил ограничения (throttling).
- Работа в крупномасштабных системах в распределённой среде.
- Возможность реализации как отдельного сервиса или как кода на уровне приложения.
- Информирование пользователей, когда их запросы ограничены.

### Требования
- Точное ограничение запросов.
- Минимальная задержка.
- Низкое потребление памяти.
- Поддержка распределённой работы.
- Понятная обработка исключений.
- Высокая отказоустойчивость.

## Шаг 3. Алгоритмы ограничения частоты запросов
### 1. Token Bucket («корзина токенов»)
<div style="margin-left:2rem">
  <img src="./images/token-bucket.png"  alt="Алгоритм Token Bucket" width="550">
</div>

- **Описание:** токены добавляются в корзину с фиксированной скоростью; каждый запрос расходует один токен.
- **Параметры:** размер корзины и скорость пополнения.
- **Плюсы:** прост в реализации, экономно расходует память, допускает всплески трафика.
- **Минусы:** требует тщательной настройки параметров.



### 2. Leaking Bucket («дырявое ведро»)
<div style="margin-left:2rem">
  <img src="./images/leaking-bucket.png"  alt="Алгоритм Leaking Bucket" width="550">
</div>

- **Описание:** обрабатывает запросы с фиксированной скоростью с помощью очереди FIFO (First In, First Out — «первым пришёл — первым ушёл»).
- **Плюсы:** экономно расходует память, обеспечивает стабильную скорость исходящего потока.
- **Минусы:** при всплесках трафика обработка новых запросов может задерживаться.
  

  Пример: https://github.com/uber-go/ratelimit



### 3. Fixed Window Counter (счётчик в фиксированном окне)
<div style="margin-left:2rem">
  <img src="./images/fixed-window-counter.png"  alt="Счётчик в фиксированном окне" width="550">
</div>

- **Описание:** делит время на фиксированные интервалы и ограничивает запросы с помощью счётчиков.
- **Плюсы:** простой, эффективен для определённых сценариев.
- **Минусы:** всплески трафика на границах окон могут приводить к превышению лимитов.

- Резкий всплеск трафика на границах временных окон
может привести к тому, что будет пропущено больше запросов, чем допускает квота.

  <img src="./images/fixed-window-issue.png"  alt="Проблема фиксированного окна" width="550">


### 4. Sliding Window Log (журнал скользящего окна)
<div style="margin-left:2rem">
  <img src="./images/sliding-window-log.png"  alt="Журнал скользящего окна" width="550">
</div>

- **Описание:** хранит временные метки запросов, реализуя скользящее временное окно.
- **Плюсы:** точное ограничение частоты запросов.
- **Минусы:** высокое потребление памяти.
  


### 5. Sliding Window Counter (счётчик скользящего окна)
<div style="margin-left:2rem">
  <img src="./images/sliding-window-counter.png"  alt="Счётчик в фиксированном окне" width="550">
</div>

- **Описание:** сочетает методы фиксированного окна и журнала скользящего окна, сглаживая всплески.
- **Плюсы:** экономно расходует память, справляется со всплесками трафика.
- **Минусы:** из-за приближённых вычислений ограничение может быть не абсолютно строгим.

## Дополнительные аспекты
### Распределённая среда
- **Проблемы:** состояние гонки (race condition), проблемы синхронизации.
- **Решения:** используйте блокировки, Lua-скрипты или отсортированные множества (sorted sets) в Redis. Для синхронизации применяйте централизованные хранилища данных.

### Оптимизация производительности
- Размещение в нескольких дата-центрах для снижения задержки.
- Модели согласованности в конечном счёте (eventual consistency) для синхронизации.

### Мониторинг
- Регулярный анализ, чтобы убедиться в эффективности алгоритма и при необходимости скорректировать правила.
