# Глава 16: Сервис поиска ближайших объектов (Proximity Service)

## Введение
**Сервис поиска ближайших объектов (proximity service)** предназначен для поиска мест поблизости: ресторанов, отелей, заправок и других заведений. Такая функциональность используется в приложениях вроде **Google Maps** и **Yelp**, чтобы пользователи могли находить места в пределах заданного радиуса.


## Шаг 1: Понимание задачи и определение границ

### **Функциональные требования**
1. **Поиск заведений** по местоположению пользователя (широта, долгота) и радиусу поиска.
2. **Владельцы заведений могут** добавлять, обновлять и удалять заведения (не в реальном времени).
3. **Предоставление подробной информации о заведении** по запросу.

### **Нефункциональные требования**
- **Низкая задержка (latency)**: пользователи должны быстро получать ответы.
- **Конфиденциальность данных**: соответствие требованиям GDPR (General Data Protection Regulation — Общий регламент ЕС по защите персональных данных) и CCPA (California Consumer Privacy Act — калифорнийский закон о защите конфиденциальности потребителей).
- **Высокая доступность**: система должна выдерживать пиковые нагрузки в часы пик в оживлённых районах.

### **Грубая оценка (Back-of-the-Envelope Estimation)**
- **100 млн DAU (Daily Active Users — число уникальных активных пользователей за день)**.
- **200 млн заведений** в системе.
- **Расчёт QPS (Queries Per Second — запросов в секунду) поиска**:
  - Пользователь выполняет **5 поисковых запросов в день**.
  - **QPS поиска** = (100M × 5) / 86,400 ≈ **5,000 QPS**.

## Шаг 2: Высокоуровневый дизайн

### **Проектирование API**
#### **Поиск заведений поблизости**
GET /v1/search/nearby

- **Параметры запроса**:
  - `latitude`: широта местоположения пользователя.
  - `longitude`: долгота местоположения пользователя.
  - `radius`: радиус поиска (по умолчанию: 5000 м).

#### **API для заведений**
| API Endpoint (API — Application Programming Interface, программный интерфейс; endpoint — конечная точка) | Описание                                         |
|-----------------------------------|--------------------------------------------------|
| `GET /v1/businesses/{id}`         | Получить подробную информацию о заведении        |
| `POST /v1/businesses`             | Добавить новое заведение                         |
| `PUT /v1/businesses/{id}`         | Обновить данные заведения                        |
| `DELETE /v1/businesses/{id}`      | Удалить заведение из системы                     |


### **Модель данных**
- Поскольку объём чтения высок из-за двух очень часто используемых функций, хорошо подходит реляционная база данных, например MySQL:
  - Поиск заведений поблизости
  - Просмотр подробной информации о заведении

### **Схема данных**
- Ключевые таблицы базы данных — таблица заведений (business) и таблица геопространственного индекса.
- Таблица заведений содержит подробную информацию о каждом заведении.

### **Высокоуровневая архитектура системы**
Система состоит из двух частей: сервиса геолокационного поиска (Location-Based Service, LBS) и сервиса заведений (business service).

<div style="margin-left:3rem">
    <img src="./images/high-level-design.png" alt="Высокоуровневый дизайн" width="400" />
</div>

- **Сервис геолокационного поиска (Location-Based Service, LBS)**:
  - Обрабатывает поисковые запросы по местоположению.
  - Сервис с преобладанием чтения, без запросов на запись.
  - QPS высок, особенно в часы пик в густонаселённых районах; сервис не хранит состояние (stateless).
- **Сервис заведений (Business Service)**: обрабатывает два типа запросов.
  - Владельцы заведений создают, обновляют или удаляют заведения.
  - Клиенты просматривают подробную информацию о заведении.
- **Балансировщик нагрузки (Load Balancer)**: маршрутизирует трафик к LBS и сервису заведений.
- **Кластер базы данных**:
  - Использует **архитектуру primary-replica** для нагрузок с преобладанием чтения.
  - Возможны расхождения между данными, которые читает LBS, и данными, записанными в primary-базу.
  - Такая несогласованность не является проблемой, поскольку информация о заведениях обновляется не в реальном времени.

## Шаг 3: Алгоритмы поиска ближайших заведений

### **Вариант 1: Двумерный поиск (наивный подход)**

<div style="margin-left:3rem">
    <img src="./images/2d-search.png" alt="Двумерный поиск" width="250" />
</div>

Самый интуитивный способ — нарисовать круг заданного радиуса и найти все заведения внутри него.

**SQL-запрос (SQL — Structured Query Language, язык структурированных запросов):**
```
SELECT business_id, latitude, longitude
FROM business
WHERE (latitude BETWEEN :lat - radius AND :lat + radius)
AND (longitude BETWEEN :long - radius AND :long + radius);
```
**Проблемы:**
- **Неэффективность**: требуется сканировать всю базу данных.
- **Ограниченность одномерных индексов** (по широте/долготе).

Возможное улучшение — построить индексы по столбцам долготы и широты; это немного лучше, но всё равно очень медленно.

### Более удачный подход
- Проблема предыдущего подхода в том, что индекс базы данных ускоряет поиск только по одному измерению.
- Оптимальный подход — отобразить двумерные данные в одно измерение с помощью геопространственного индексирования (geospatial indexing):
  - Хеш: равномерная сетка (even grid), geohash
  - Дерево: quadtree, Google S2, R-tree

  <div style="margin-left:3rem">
    <img src="./images/geospatial-index-types.png" alt="Типы геопространственных индексов" width="500" />
  </div>


### **Вариант 2: Равномерная сетка (Evenly Divided Grid)**

  <div style="margin-left:3rem">
    <img src="./images/even-grid.png" alt="Равномерная сетка" width="400" />
  </div>

- **Мир делится на ячейки фиксированного размера**.
- **Проблема**: заведения распределены неравномерно (высокая плотность в городах, низкая — в сельской местности).

### **Вариант 3: Geohash**
- Планета делится на четыре квадранта по нулевому меридиану и экватору. Затем каждая ячейка делится на четыре ячейки поменьше.
- Каждую ячейку можно представить, чередуя биты долготы и широты.
- Разбиение повторяется.

  <div style="margin-left:3rem">
    <img src="./images/geohash.png" alt="Geohash" width="300" />
    <img src="./images/geohash-1.png" alt="Geohash" width="285" />
  </div>


- **Кодирует широту и долготу в одну буквенно-цифровую строку**. Имеет 12 уровней точности (precision).
- **Иерархическая структура сетки** обеспечивает эффективный поиск.
- Нужная точность выбирается как минимальная длина geohash согласно таблице.
  <div style="margin-left:3rem">
    <img src="./images/geohash-radius-mapping.png" alt="Соответствие geohash и радиуса" width="400" />
  </div>
- Geohash гарантирует: чем длиннее общий префикс двух geohash, тем ближе они друг к другу.

- **Сложности**:
  <div style="margin-left:3rem">
    <img src="./images/boundary-issue.png" alt="Проблема границ" width="300" />
  </div>

  - **Проблема границ** (заведения у краёв ячейки могут не попасть в результат).
    - Две точки могут находиться очень близко, но не иметь общего префикса вовсе (например, по разные стороны экватора).
    - Две точки могут иметь длинный общий префикс, но относиться к разным geohash.
  - Решение: искать также в соседних ячейках.


### **Вариант 4: Quadtree**

  Quadtree (дерево квадрантов) — это древовидная структура данных, которая рекурсивно делит двумерное пространство на четыре квадранта; у каждого внутреннего узла ровно четыре потомка, соответствующих четырём подобластям пространства.
  - Quadtree — это структура данных в памяти (in-memory); она работает на каждом сервере LBS и строится при запуске сервера.

  <div style="margin-left:3rem">
    <img src="./images/quadtree.png" alt="Quadtree" width="500" />
  </div>

  - Корневой узел рекурсивно разбивается на 4 квадранта, пока ни в одном узле не останется больше x заведений (в данном случае 100).

  <div style="margin-left:3rem">
    <img src="./images/building-quadtree.png" alt="Построение quadtree" width="500" />
  </div>

- Индекс quadtree занимает не так много памяти (обычно единицы ГБ) и легко помещается на одном сервере.
- Поскольку сложность построения дерева — n log n, построение может занять несколько минут.
- **Эффективен для запросов поиска k ближайших (k-nearest)** (например, найти ближайшую заправку).

  <div style="margin-left:3rem">
    <img src="./images/realworld-quadtree.png" alt="Quadtree на реальных данных" width="400" />
  </div>

#### Эксплуатационные аспекты
 - Для примерно 200 млн заведений построение quadtree при запуске сервера может занять несколько минут.
 - Пока quadtree строится, сервер не может обслуживать трафик, поэтому новый релиз следует выкатывать постепенно на часть серверов.
 - При обновлении или добавлении заведения проще всего инкрементально перестраивать quadtree (что приводит к массовой инвалидации кеша).
 - Также можно обновлять quadtree «на лету», но это сложнее в реализации (нужен механизм блокировок).

### **Вариант 5: Google S2**
Отображает сферу в одномерный индекс на основе кривой Гильберта (Hilbert curve). Две точки, близкие друг к другу на кривой Гильберта, близки и в одномерном пространстве.


  <div style="margin-left:3rem">
    <img src="./images/hilbert-curve.png" alt="Кривая Гильберта" width="300" />
    <img src="./images/geofence.png" alt="Геозона" width="355" />
  </div>

- **Делит Землю на небольшие ячейки с помощью кривой Гильберта**.
- Отлично подходит для геозонирования (geofencing), поскольку может покрывать произвольные области ячейками разных уровней.
- Геозонирование также позволяет задавать периметры вокруг интересующей области.
- Ещё одно преимущество: вместо фиксированного уровня точности в S2 можно указать минимальный и максимальный уровень и максимальное число ячеек.


## Сравнение компромиссов

#### Geohash
- Прост в использовании и реализации — не нужно строить/перестраивать дерево.
- Поддерживает выдачу результатов в фиксированном радиусе.
- Индекс легко обновлять.
- Нельзя динамически подстраивать размер ячейки под плотность населения.

#### Quadtree
- Реализовать немного сложнее.
- Поддерживает получение k ближайших заведений.
- Может динамически подстраивать размер ячейки под плотность населения.
- Обновление индекса сложнее, так как может потребоваться перестроить всё дерево.

## Шаг 4: Масштабирование базы данных и стратегия кеширования

### **Масштабирование таблицы заведений**
- **Шардирование по business ID (ID — Identifier, идентификатор)** обеспечивает равномерное распределение данных.
- Для каждого заведения в таблице отдельная строка.

| Geohash | Business ID |
|---------|------------|
| 9q9hvu  | 343        |
| 9q9hvu  | 347        |
| 9q9hvu  | 112        |

### **Масштабирование геопространственного индекса**
- Для таблицы geohash шардирование может не подойти. В данном случае всё помещается на одном сервере, поэтому технических причин для шардирования нет.
- Лучший подход — использовать реплики для чтения (read replicas), чтобы справиться с нагрузкой на чтение.



---

### **Стратегия кеширования**
Самый очевидный выбор ключа кеша — координаты местоположения, однако у него есть несколько проблем:
 - Координаты с GPS (Global Positioning System — глобальная система позиционирования) неточны.
 - Пользователь может перемещаться, из-за чего координаты меняются.
 - Лучший ключ — geohash.

| Ключ кеша  | Значение в кеше |
|------------|------------|
| `geohash`  | Список ID заведений в этой ячейке |
| `business_id` | Данные заведения (название, адрес, отзывы и т. д.) |

## Шаги получения ближайших заведений
1. **Запрос пользователя:**  
   - Пользователь ищет рестораны в радиусе **500 метров**.  
   - Клиент отправляет **широту (37.776720), долготу (-122.416730) и радиус (500m)** на **балансировщик нагрузки**.

2. **Перенаправление запроса:**  
   - **Балансировщик нагрузки (LB — Load Balancer)** перенаправляет запрос в **сервис геолокационного поиска (LBS)**.

3. **Вычисление geohash:**  
   - LBS определяет **длину geohash**, соответствующую радиусу.  
   - По справочной таблице **500 м соответствует длина geohash = 6**.

4. **Получение соседних geohash:**  
   - LBS вычисляет **соседние geohash**, чтобы охватить близлежащие области.  
   - Результат — список:  
     ```
     [my_geohash, neighbor1_geohash, neighbor2_geohash, ..., neighbor8_geohash]
     ```

5. **Получение ID заведений из Redis:**  
   - Для каждого geohash из списка LBS обращается к **Redis-серверу geohash** за **ID заведений**.  
   - Запросы выполняются параллельно, чтобы минимизировать задержку.

6. **Получение и ранжирование заведений:**  
   - LBS получает **полные данные заведений** из **Redis-сервера с информацией о заведениях**.  
   - Заведения **сортируются по расстоянию** от местоположения пользователя.  
   - **Ранжированные результаты** возвращаются клиенту.

## Ключевые оптимизации
- **Параллельные обращения к Redis**: сокращают время ответа.  
- **Индексирование по geohash**: обеспечивает эффективные пространственные запросы.  
- **Кеширование**: ускоряет поиск и получение данных о заведениях.  

Этот метод обеспечивает **масштабируемое получение с низкой задержкой** заведений рядом с пользователем.

### **Выбор оптимального метода индексирования**
| Метод индексирования | Плюсы | Минусы |
|----------------|------|------|
| **Geohash** | Прост в реализации, эффективен для поиска ближайших объектов | Проблема границ, фиксированный размер ячейки |
| **Quadtree** | Динамически подстраивается под плотность, поддерживает запросы k ближайших | Сложнее, требует перебалансировки дерева |
| **Google S2** | Продвинутое геозонирование, используется в Google Maps | Сложнее в реализации |
