# Глава 12: Проектирование чата

## Введение
**Система чата (chat system)** обеспечивает обмен сообщениями между пользователями в реальном времени. В этой главе мы спроектируем чат-приложение, которое поддерживает:
- **Личные чаты (один на один)**
- **Групповые чаты (до 100 пользователей)**
- **Индикаторы присутствия в сети (online presence)**
- **Работу на нескольких устройствах**
- **Push-уведомления**

Система рассчитана на **50 миллионов активных пользователей в день — DAU (Daily Active Users — число уникальных пользователей, заходящих в сервис за день)** и хранит историю переписки бессрочно.

---

## Шаг 1: Понимание задачи

### Требования
1. **Функциональность:**
   - Личные и групповые чаты (до 100 участников).
   - Текстовые сообщения (до 100 000 символов).
   - Индикаторы «в сети / не в сети».
   - Поддержка нескольких устройств.
   - Push-уведомления.
2. **Масштаб:** проектирование под 50 миллионов DAU.
3. **Хранение:** бессрочное хранение истории переписки.

1. **Сторона отправителя:** HTTP (HyperText Transfer Protocol — протокол передачи гипертекста) для отправки сообщений с использованием постоянных соединений (persistent connections) для повышения эффективности.

2. **Сторона получателя:**
   - **Опрос (polling):**
      - Клиент периодически спрашивает сервер, есть ли новые сообщения.
      - Неэффективно из-за частых избыточных запросов.

   - **Длинный опрос (long polling):** 
      - Соединение остаётся открытым, пока не придут сообщения. 
      - Неэффективно для неактивных пользователей.

         <img src="./images/long-polling.png" alt="Длинный опрос (long polling)" width="400">

   - **WebSocket:** 
      - Двунаправленное постоянное соединение для обмена данными в реальном времени; выбрано как для отправки, так и для получения сообщений.
      - Для отправки и получения сообщений используется протокол WebSocket (ws — схема URL протокола WebSocket, ws://).

1. **Сервисы без состояния (stateless services):**
   - Отвечают за регистрацию, вход и управление профилем пользователя.
   - Интегрированы с механизмом обнаружения сервисов (service discovery), который подбирает оптимальный чат-сервер.
2. **Сервисы с состоянием (stateful services):**
   - Чат-серверы поддерживают постоянные WebSocket-соединения.
   - Отвечают за доставку и синхронизацию сообщений.
3. **Интеграция со сторонними сервисами:**
   - Сервисы push-уведомлений оповещают пользователей о новых сообщениях.
   - Реализация уведомлений описана в главе «Система уведомлений».

### Дизайн

Клиент поддерживает постоянное WebSocket-соединение с чат-сервером для обмена сообщениями в реальном времени.

<div style="margin-left:3rem">
      <img src="./images/high-level-design.png" alt="Высокоуровневый дизайн" width="450"> 
</div>

- Чат-серверы обеспечивают отправку и получение сообщений.
- Серверы присутствия (presence servers) управляют статусом «в сети / не в сети».
- API-серверы (API — Application Programming Interface, программный интерфейс приложения) обрабатывают всё остальное, включая вход пользователя, регистрацию, изменение профиля и т. д.
- Серверы уведомлений отправляют push-уведомления.
- Наконец, для хранения истории переписки используется хранилище «ключ–значение» (key-value store). Key-value хранилища выбраны в качестве базы данных для истории чатов по следующим причинам:
   - Они легко масштабируются горизонтально.
   - KV-хранилища (KV — key-value, «ключ–значение») обеспечивают очень низкую задержку доступа к данным.
   - Реляционные базы данных плохо справляются с «длинным хвостом» (long tail) данных. Когда индексы разрастаются,
   произвольный доступ становится дорогим.
   - KV-хранилища используются другими проверенными и надёжными чат-приложениями, например
   Facebook Messenger и Discord.


Ниже приведены модели данных для личного и группового чата.
   - Первичный ключ — ID (identifier — идентификатор) сообщения, который помогает определить порядок сообщений.
   - Для группового чата используется составной первичный ключ (channel_id, message_id). 
      - ID можно генерировать с помощью глобального генератора 64-битных последовательных номеров, например Snowflake.
      - Более удачный подход — использовать локальный генератор последовательных номеров. «Локальный» означает, что ID уникальны только в пределах группы.
      - Локальные ID работают, потому что достаточно поддерживать порядок сообщений в пределах одного личного или группового канала.

## Шаг 3: Детальный разбор дизайна

### Обнаружение сервисов (service discovery)

<div style="margin-left:3rem">
   <img src="./images/zookeeper.png" alt="Zookeeper" width="400">   
</div>

- Основная задача обнаружения сервисов — подобрать для клиента оптимальный чат-сервер
на основе таких критериев, как географическое положение и ёмкость сервера. 
- Для распределения чат-серверов по таким критериям, как географическое положение и ёмкость сервера, используется **Apache Zookeeper**.
- Обеспечивает эффективное распределение нагрузки и минимизирует задержку.


### Потоки сообщений
#### Личный чат


1. Пользователь A отправляет сообщение на чат-сервер 1.
2. Чат-сервер 1 присваивает сообщению уникальный ID и сохраняет его в key-value хранилище.
3. Если пользователь B в сети, сообщение пересылается на чат-сервер 2, который поддерживает с ним постоянное WebSocket-соединение.
4. Если пользователь B не в сети, отправляется push-уведомление.



#### Групповой чат

<div style="margin-left:3rem">
   <img src="./images/group-chat-flow.png" alt="Поток сообщений группового чата" width="400">  
</div>

- Сообщения копируются в отдельные входящие ящики (inbox) каждого получателя в группе.
- Это упрощает синхронизацию, но становится дорогим для больших групп.
- На стороне получателя сообщения могут приходить от нескольких пользователей. У каждого получателя
есть входящий ящик (очередь синхронизации сообщений), содержащий сообщения от разных отправителей.

---

#### Синхронизация сообщений

У многих пользователей несколько устройств, поэтому сообщения нужно синхронизировать между ними.
Каждое устройство хранит переменную cur_max_message_id, в которой отслеживается ID последнего
сообщения на устройстве. Новыми считаются сообщения, удовлетворяющие двум
условиям:

<div style="margin-left:3rem">
   <img src="./images/message-synchronization.png" alt="Синхронизация сообщений"  width="400">  
</div>

- ID получателя совпадает с ID текущего вошедшего пользователя.
- ID сообщения в key-value хранилище больше, чем cur_max_message_id.

### Присутствие в сети (online presence)
1. **Механизм heartbeat:** 
   <div style="margin-left:3rem">
      <img src="./images/heartbeat-mechanism.png" alt="Механизм heartbeat" width="400"> 
   </div>
   
   - Клиенты периодически отправляют heartbeat-сигналы серверам присутствия, сообщая, что они в сети. 
   - Если heartbeat не получен в течение порогового времени (например, x = 30), пользователь помечается как «не в сети».

     

2. **Модель рассылки (fanout):** 

   <div style="margin-left:3rem">
      <img src="./images/fanout-presence.png" alt="Рассылка статуса присутствия" width="400"> 
   </div>

   - Обновления статуса присутствия рассылаются друзьям по модели «издатель–подписчик» (publish-subscribe), в которой для каждой пары друзей существует отдельный канал.
   - Когда меняется онлайн-статус пользователя A, событие публикуется в три канала: A-B, A-C и A-D. 
   - На эти три канала подписаны соответственно пользователи B, C и D, которые и получают обновления статуса.
   - Такой дизайн эффективен для небольших групп пользователей.

## Дополнительные соображения
### Масштабируемость
- **Горизонтальное масштабирование:** добавление серверов по мере роста числа пользователей.
- **Балансировка нагрузки:** равномерное распределение трафика по серверам.
- **Кеширование:** снижение нагрузки на базу данных и уменьшение задержки.

### Обработка ошибок
- **Механизмы повторных попыток:** обработка сбоев доставки сообщений с помощью повторов и очередей.
- **Отказы серверов:** использование обнаружения сервисов для выделения новых серверов при сбоях.

### Возможные расширения
1. **Поддержка медиа:** обработка фотографий и видео, включая сжатие и облачное хранение.
2. **Сквозное шифрование (end-to-end encryption):** обеспечение конфиденциальности сообщений.
3. **Кеширование на стороне клиента:** сокращение объёма передаваемых данных для повышения производительности.
4. **Ускорение загрузки:** использование географически распределённых сетей кеширования.
