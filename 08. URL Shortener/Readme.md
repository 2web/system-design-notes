# Глава 8. Проектирование сервиса сокращения ссылок (URL Shortener)

## Введение
В этой главе рассматривается проектирование сервиса сокращения ссылок, подобного TinyURL. Основные задачи системы — **сокращение URL** (Uniform Resource Locator — адрес ресурса в интернете), **перенаправление (редирект)** и **высокая масштабируемость** для обработки больших объёмов трафика.

### Требования
- Сокращённые URL должны быть **уникальными** и **как можно более короткими**.
- Обработка **100 миллионов генераций URL в день** с запасом на 10 лет работы.
- Поддержка **эффективных операций чтения** при соотношении чтения к записи 10:1.
- Хранение 365 миллиардов записей, что потребует примерно **365 TB** хранилища за 10 лет.

## Шаг 1. Высокоуровневый дизайн

### Эндпоинты API (Application Programming Interface — программный интерфейс приложения)
1. **Сокращение URL:**  
   - Эндпоинт: `POST api/v1/data/shorten`  
   - Параметры: `{longUrl: longURLString}`  
   - Возвращает: `shortURL`

2. **Перенаправление по URL:**  
   - Эндпоинт: `GET api/v1/shortUrl`  
   - Возвращает: `longURL` для перенаправления.

### Перенаправление по URL
- **Редирект 301:**  редирект 301 означает, что запрошенный URL «навсегда» перемещён на длинный URL. Браузер кэширует ответ, и
последующие запросы по тому же URL уже не отправляются в сервис сокращения ссылок.
- **Редирект 302:** временный; полезен для аналитики, например для отслеживания кликов.

### Сокращение URL
<p align="center">
    <img src="./images/url-shortening.png" alt="Сокращение URL" width="400">
</p>

- Для генерации короткого URL используется **хеш-функция**, сопоставляющая длинным URL уникальные сокращённые версии.
- Хеш-функция должна удовлетворять следующим требованиям:
    - Каждый longURL должен хешироваться в одно значение hashValue.
    - Каждое значение hashValue должно однозначно сопоставляться обратно с longURL.

## Шаг 2. Детальная проработка дизайна

### Модель данных
Сопоставления `<shortURL, longURL>` хранятся в реляционной базе данных для оптимизации использования памяти. Схема таблицы включает:
- `id` (первичный ключ),
- `shortURL`,
- `longURL`.

    <img src="./images/table-schema.png" alt="Схема таблицы" width="300">

### Хеш-функция
#### 1. Преобразование в Base 62:
- Числа кодируются символами `[0-9, a-z, A-Z]`, что даёт **62 возможных символа**.
- Преобразование системы счисления — ещё один подход, часто используемый в сервисах сокращения ссылок. 
- Короткому URL можно присвоить уникальный ID (Identifier — идентификатор), а затем преобразовать этот ID в Base 62, чтобы получить короткий URL.
- 7-символьный хеш позволяет получить до **3.5 триллиона уникальных URL**, чего достаточно для 365 миллиардов URL.

**Пример:**  
Преобразование ID `2009215674938` в Base 62:
- `2009215674938` → `zn9edcu`.

#### 2. Хеш + разрешение коллизий:
- Используются хеш-функции, такие как CRC32 (Cyclic Redundancy Check — циклический избыточный код), MD5 (Message Digest 5) или SHA-1 (Secure Hash Algorithm 1).

    <img src="./images/hash-function.png" alt="Хеш-функция" width="500">

- Один из подходов — брать первые 7 символов хеш-значения, однако такой метод может приводить к коллизиям хешей.
- Для разрешения коллизий можно рекурсивно добавлять новую заранее заданную строку, пока коллизии не исчезнут, но это может быть дорого.
- Для эффективного поиска при разрешении коллизий используются **фильтры Блума (Bloom filters)**.

    <p align="center">
    <img src="./images/url-lookup.png" alt="Поиск URL" width="500">
    </p>

### Сравнение

-  **Хеш + разрешение коллизий:**
    - Фиксированная длина короткого URL
    - Не нужен генератор уникальных ID
    - Возможны коллизии, которые необходимо разрешать
    - Невозможно найти следующий доступный короткий URL, так как он не зависит от ID

- **Преобразование в Base 62**
    - Длина не фиксирована и растёт вместе с ID
    - Нужен генератор уникальных ID
    - Коллизии невозможны
    - Легко вычислить следующий короткий URL, если ID увеличивается на 1 (может представлять угрозу безопасности)

### Процесс сокращения URL

<p align="center">
    <img src="./images/url-shortening-flow.png" alt="Сокращение URL" width="500">
</p>

1. Проверить, есть ли `longURL` в базе данных.
2. Если есть, вернуть существующий `shortURL`.
3. В противном случае:
   - Сгенерировать уникальный ID с помощью **распределённого генератора ID**.
   - Преобразовать ID в `shortURL` с помощью Base 62.
   - Сохранить сопоставление `<id, shortURL, longURL>` в базе данных.



---

### Процесс перенаправления по URL
<p align="center">
    <img src="./images/url-redirecting-flow.png" alt="Сокращение URL" width="600">
</p>

1. Пользователь переходит по `shortURL`.
2. Запрашивается сопоставление `<shortURL, longURL>`:
   - Сначала проверяется **кэш** для более быстрого доступа.
   - Если в кэше данных нет, выполняется запрос к базе данных.
3. Пользователь перенаправляется на `longURL`.

## Дополнительные аспекты
### Ограничитель запросов (Rate Limiter)
- Защита от злоупотреблений за счёт ограничения числа запросов с одного IP-адреса (IP — Internet Protocol).

### Масштабируемость
1. **Веб-уровень:** stateless, масштабируется добавлением/удалением веб-серверов.
2. **Уровень базы данных:** используются репликация и шардирование.

### Аналитика
- Сбор данных, таких как частота кликов, источник переходов и временные метки, для бизнес-аналитики.

### Высокая доступность и надёжность
- Обеспечение согласованной и надёжной работы сервиса за счёт репликации базы данных и отказоустойчивой архитектуры.
