# Глава 15: Проектирование Google Drive

## Введение
Google Drive — облачный сервис хранения и синхронизации файлов, позволяющий пользователям хранить файлы, получать к ним доступ и делиться ими с разных устройств. В этой главе рассматривается проектирование масштабируемой системы со следующими возможностями:
- **Загрузка и скачивание файлов**
- **Синхронизация файлов между устройствами**
- **Совместный доступ к файлам**
- **История изменений (ревизий) файлов**
- **Уведомления о редактировании, удалении и предоставлении доступа**

---

## Шаг 1: Понимание задачи

### Ключевые требования
#### Функциональные требования:
- Загрузка и скачивание файлов.
- Синхронизация файлов между несколькими устройствами.
- Хранение ревизий файлов.
- Совместный доступ к файлам с управлением правами.
- Отправка уведомлений о редактировании, удалении файлов и предоставлении доступа к ним.

#### Нефункциональные требования:
- **Надёжность:** потеря данных недопустима.
- **Высокая скорость синхронизации:** не заставлять пользователей ждать из-за задержек синхронизации.
- **Экономия пропускной способности:** минимизировать лишний расход трафика.
- **Масштабируемость:** обслуживать 10 миллионов активных пользователей в день — DAU (Daily Active Users — число уникальных пользователей, заходящих в сервис за день).
- **Высокая доступность:** бесперебойная работа при отказах серверов или проблемах с сетью.

### Ограничения и допущения
- Пользователи получают **10 ГБ бесплатного пространства**.
- Максимальный размер файла: **10 ГБ**.
- Средний размер загружаемого файла: **500 КБ**.
- Частота загрузки: **2 файла в день на пользователя**.
- Общий требуемый объём хранилища: **500 ПБ**.

## Шаг 2: Высокоуровневый дизайн
### Конфигурация с одним сервером
Базовая конфигурация включает:
1. **Веб-сервер:** обрабатывает загрузку и скачивание.
2. **База данных метаданных:** отслеживает метаданные, такие как данные пользователей, информация о входе, информация о файлах.
3. **Каталог хранилища:** содержит файлы, организованные по пространствам имён (namespaces).


<div style="margin-left:3rem">
    <img src="./images/namespaces.png" alt="Пространства имён" width="400" />
</div>

- Настраивается веб-сервер, а в качестве корневого каталога для хранения загруженных файлов используется каталог drive/. 
- Внутри каталога drive/ находится набор каталогов — пространств имён. 
- Каждое пространство имён содержит все файлы, загруженные соответствующим пользователем. 
- Каждый файл или папку можно однозначно идентифицировать, объединив пространство имён и относительный путь.


Этот дизайн служит отправной точкой, но непригоден для масштабирования.

#### API (Application Programming Interface — программный интерфейс приложения)
1. **Загрузка файла в Google Drive:** поддерживаются два типа загрузки
    - Простая загрузка (simple upload): используется для файлов небольшого размера.
    - Возобновляемая загрузка (resumable upload): 
        - Эндпоинт: https://api.example.com/files/upload?uploadType=resumable
        - Отправить начальный запрос, чтобы получить URL (Uniform Resource Locator — адрес ресурса) для возобновляемой загрузки.
        - Загрузить данные и отслеживать состояние загрузки.
        - Если загрузка прервалась, возобновить её.
2. **Скачивание файла из Google Drive:** для скачивания файла
    -  Эндпоинт: https://api.example.com/files/download
3. **Получение ревизий файла:**
    - Эндпоинт: https://api.example.com/files/list_revisions

### Переход к распределённой системе

#### Улучшения:
1. **Шардирование:** распределение хранилища по серверам на основе `user_id`.
2. **Amazon S3:** использование S3 (Simple Storage Service — объектное хранилище AWS) для масштабируемого и избыточного хранения файлов с межрегиональной репликацией.

    <img src="./images/replication.png" alt="Репликация" width="600" />
     
3. **Балансировщик нагрузки:** распределение трафика между несколькими веб-серверами.
4. **Репликация базы данных метаданных:** обеспечение доступности за счёт шардирования и репликации базы данных.


#### Конфликты синхронизации:
В крупной системе хранения, такой как Google Drive, конфликты синхронизации время от времени неизбежны.
Конфликт возникает, когда два пользователя одновременно изменяют один и тот же файл или папку.

<div style="margin-left:5rem">
<img src="./images/sync-conflicts.png" alt="Конфликты синхронизации" width="600" />
</div>

- В примере пользователь 1 и пользователь 2 одновременно пытаются обновить один и тот же файл, но файл пользователя 1 обрабатывается системой первым.
- Операция обновления пользователя 1 проходит успешно, а пользователь 2 получает конфликт синхронизации. 
- Система показывает обе копии файла: локальную копию пользователя 2 и последнюю версию с сервера.
- Пользователь 2 может объединить оба файла или заменить одну версию другой.

### Улучшенный дизайн
<div style="margin-left:5rem">
<img src="./images/high-level-design.png" alt="Высокоуровневый дизайн" width="500" />
</div>

1. **Взаимодействие с пользователем:** пользователи работают с приложением через браузер или мобильное приложение.

2. **Блочные серверы (block servers):**
   - Файлы разбиваются на **блоки по 4 МБ** (максимальный размер), каждому из которых присваивается уникальное хеш-значение.
   - Блоки хранятся в облачном хранилище независимо друг от друга (например, в Amazon S3).
   - Восстановление файла сводится к объединению блоков в определённом порядке.

3. **Облачное хранилище:** блоки хранятся в облачном хранилище для обеспечения масштабируемости и избыточности.

4. **Холодное хранилище (cold storage):** неактивные файлы переносятся в холодное хранилище для снижения затрат.

5. **Балансировщик нагрузки:** равномерно распределяет запросы между API-серверами для эффективной работы.

6. **API-серверы:**
   - Отвечают за аутентификацию пользователей, управление профилями и обновление метаданных файлов.
   - Обслуживают все процессы, кроме загрузки файлов.

7. **База данных метаданных и кеш:**
   - Хранит метаданные пользователей, файлов, блоков и версий.
   - Часто запрашиваемые метаданные кешируются для ускорения доступа.

8. **Сервис уведомлений:**
   - **Система «издатель–подписчик» (publisher/subscriber)**, уведомляющая клиентов об изменениях файлов (добавление, редактирование, удаление).
   - Обеспечивает клиентам возможность получать последние обновления.

9. **Очередь резервирования для офлайн-клиентов (offline backup queue):** временно хранит информацию об изменениях файлов, чтобы офлайн-клиенты могли синхронизироваться, когда снова выйдут в сеть.

### Процесс загрузки файла

1. **Загрузка файла:**
   - Блочный сервер разбивает файл на блоки, сжимает и шифрует их.
   - Блоки загружаются на блочные серверы и сохраняются в S3.
2. **Загрузка метаданных:**
   - Клиент отправляет метаданные на API-сервер.
   - Метаданные сохраняются в базе данных со статусом `pending`.
3. **Завершение:**
   - S3 вызывает callback, который обновляет статус файла на `uploaded`.
   - Сервис уведомлений оповещает соответствующих пользователей.

### Синхронизация файлов
1. **Дельта-синхронизация (delta sync):** передаются только изменённые блоки, а не весь файл.

    <div style="margin-left:2rem">
    <img src="./images/delta-sync.png" alt="Дельта-синхронизация" width="400" />
    </div>

2. **Сжатие:** блоки сжимаются алгоритмами, выбираемыми в зависимости от типа файла. 
3. **Разрешение конфликтов:**
   - Побеждает версия, обработанная первой.
   - Конфликтующие версии сохраняются отдельно, чтобы пользователь мог разрешить конфликт сам.

### Процесс скачивания файла
Процесс скачивания запускается, когда файл добавлен или изменён в другом месте. Клиент может узнать об этом двумя способами:
- Если клиент A в сети, когда другой клиент изменяет файл, сервис уведомлений сообщит об этом клиенту A.
- Если клиент A не в сети, когда другой клиент изменяет файл, данные сохраняются в кеш. Когда офлайн-клиент снова выходит в сеть, он забирает последние изменения.

Узнав об изменении файла, клиент сначала запрашивает метаданные через API-серверы, а затем
скачивает блоки для восстановления файла.

1. **Триггер:** сервис уведомлений сообщает клиенту об обновлении файлов.
2. **Получение метаданных:** клиент получает обновлённые метаданные через API.
3. **Скачивание блоков:** клиент скачивает обновлённые блоки с блочных серверов и восстанавливает файл.

### Сервис уведомлений
1. **Назначение:** информирует клиентов об изменениях файлов.
2. **Механизм:** использует **длинный опрос (long polling)** для асинхронных уведомлений.
3. **Пример:** при добавлении, редактировании или удалении файла уведомления отправляются всем соответствующим клиентам.


---

### Оптимизация хранения
1. **Дедупликация:** удаление дублирующихся блоков на уровне аккаунта с помощью сравнения хешей.
2. **Стратегия версионирования:**
   - Ограничивать количество сохраняемых ревизий.
   - Для часто редактируемых файлов отдавать приоритет последним версиям.
3. **Холодное хранилище:** перенос редко используемых файлов в более дешёвые решения для хранения (например, Amazon S3 Glacier).

---

### Обработка отказов
1. **Отказ балансировщика нагрузки:** активируется резервный балансировщик.
2. **Отказ блочного сервера:** незавершённые задачи переназначаются другим серверам.
3. **Отказ базы данных метаданных:**
   - Повысить подчинённый узел (slave) до ведущего (master).
   - Перенаправить трафик на оставшиеся реплики.
4. **Отказ облачного хранилища:** использовать межрегиональную репликацию для получения недоступных файлов.
5. **Отказ сервиса уведомлений:** клиенты переподключаются к альтернативным серверам.
